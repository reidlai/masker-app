- (decision) AD-12 (App-Boot Unified Reactive Bio-Signal Ingestion Queue). Binds: app bootstrap/main(), BLE background receiver service, every IBLESensorDriver impl, and all downstream consumers (BleBloc, ApneaEvaluator, MeasurementPage, Stage-1/Stage-2 calibration, SleepMonitoringBloc). Prevents: per-screen/per-phase BLE subscriptions each opening their own GATT channel; divergent queue primitives (plain StreamController/PublishSubject) that drop latest-value replay for late subscribers; calibration vs monitoring racing to own the connection lifecycle. Rule: on launch the receiver service starts (Android foreground service connectedDevice/dataSync type; iOS bluetooth-central UIBackgroundModes) and binds exactly one active IBLESensorDriver by DI; every inbound sample (physical GATT notification OR BleTelemetryService simulator tick) is pushed via .add() into a single process-wide BehaviorSubject<double> exposed as thermalStream/signalStream; all consumers subscribe to that one ValueStream and none open their own BLE subscription or a second queue; queue identity is stable across a driver swap.
- (assumption) Boot starts the receiver SERVICE + unified queue + DI-bound driver; the physical BLE radio connection (scanAndConnect) stays lazy — established when a bound D-BAND is in range or the first consumer needs it, then held alive by the foreground service for the session. Rationale: preserves AD-06 <8% / 8h battery budget and avoids boot-time scans with no device bound. Simulator driver (in-process) streams from boot. FLAG for user confirmation: alternative reading of FR-1.11 is a truly always-on radio link from launch.

- (decision) AD-13 (Subscription State & Server-Verified Entitlement). Binds: backend Billing service, Flutter BillingBloc/SubscriptionRepository/EntitlementService, every plan-gated feature call (today: Doctor Report Export / Task_ExportDoctorReport), the Stripe webhook receiver. Prevents: the client trusting a local plan flag to unlock a gated feature; multiple components deciding 'is this user Premium?' from different sources; a gated clinical action hard-blocking a patient when the entitlement server is briefly unreachable. Rule: our backend Billing service is the SOLE source of truth for subscription state, updated only by HMAC-signature-verified Stripe webhook events (customer.subscription.*, invoice.*); Stripe EXECUTES PAYMENT ONLY -- plan lifecycle (create/change/cancel/invoice history) is owned by our backend (user picked PaymentSheet + custom subscription backend). The client fetches a signed entitlement claim and MAY cache it; a plan-gated action re-checks server-side and on transport failure falls back to the cached claim within a bounded grace window (fail-open for connectivity, never for a known-expired plan). Entitlement is never derived client-side from raw Stripe data.
- (decision) AD-14 (Cardholder-Data Scope Containment -- PCI-DSS SAQ-A). Binds: MOB_PAYMENT_METHOD / StripePaymentSheetGateway, the Billing service, every datastore and log on the platform. Prevents: any client or backend component receiving, storing, transiting, or logging a PAN, CVC, full expiry, or track data; a hand-rolled in-app card-entry form. Rule: card capture occurs ONLY inside Stripe's hosted PaymentSheet (mobile) / Stripe Elements (web); the platform persists and renders ONLY the display triplet (brand, last4, exp_month/exp_year) plus the opaque stripe_payment_method_id. No platform component enters the cardholder-data environment => platform stays PCI-DSS SAQ-A eligible. Card-on-file add/replace go through PaymentSheet; 'remove card' detaches the token via the Billing service.
